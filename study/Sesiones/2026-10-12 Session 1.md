# Where to improve

## Technical
- Idempotency key lifecycle: one key per payment **intent**, created once and persisted, reused on every retry. Not a hash of the cart (legit repeat sales collide), not a per-tap timestamp (each retry gets a new key).
- The duplicate must **return the first result**, not be "skipped". A network error after sending is an **unknown** state, not a failure.
- A system-prompt rule is **not a security control** against prompt injection: instructions and data share one channel. Defences live outside the model — least privilege, the tool call authorised with the *user's* permissions, human confirmation for writes, audit log.
- `'use client'` components are **still server-rendered**. Anything that differs between server and browser (`Math.random`, `Date.now`, `localStorage`, `typeof window` branches, default `Intl` locale) breaks hydration. Fixes: `useId`, `useSyncExternalStore` with a server snapshot, compute after mount, or move the data to a cookie the server can read.

## Answer habits
- Answered one half of a two-part question (backend dedupe) and never reached the other (what the associate sees).
- 🔁 Typed `next` with the follow-ups still open (Q1, Q2, Q4), and once without answering at all (Q3). In a real round the panel doesn't move on; an unanswered follow-up reads as "doesn't know". Say "I'm not sure, my guess is…" instead.
- Code challenge answered without code (Q2). Even a partial component is graded higher than none.
- Changed the design under a follow-up (hash → timestamp) without saying which one you keep and why.

## English
- "unic" → **unique**; "identicator" → **identifier**; "skiped" → **skipped**. Say "idempotency key" — it's the term the panel is waiting for.

# Questions

## 1. [Nordstrom · EXTRA] Charging a card exactly once on a flaky store network — ⚠️

**Question:** A store associate taps "Pay" on POS+, the card terminal approves, but the store Wi-Fi drops before our frontend gets the response. The associate sees a spinner, then an error, and taps "Pay" again. The customer is charged twice. How do you design the payment flow, frontend and the contract with the backend, so this cannot happen?
*Follow-ups:* (1) Same $20 scarf sold twice, five minutes apart, same card — what happens with a hash-based ID? What does the backend return for the duplicate, and what does the associate see? (2) When exactly is the ID created and where does it live — same ID or new one on the second tap? Unanswered — moved on with `next`.

**What I said:** "have a unique identifier, creating a unique id with crypto using the info of the transaction … if the backend receives 2 charges with the same id the second one has to be skipped" · "we can use the timestamp or the transaction id of the terminal to generate it".

**What was wrong or missing:** A hash of the transaction data makes two legitimate identical sales collide. A timestamp taken at tap time gives the retry a new key, so it double-charges again. The key identifies the payment *intent*: `crypto.randomUUID()` once when the payment starts, persisted (state + IndexedDB to survive a reload), reused on every retry. The server stores key → result and **replays the first response**; same key with a different payload → 422; still processing → 409/202 and the client polls. Frontend: single-flight + disabled Pay, and a network error after sending is "unknown" — show "Checking payment…" and query status by key before allowing a retry. Never answered what the associate sees.

**Missing beat:** 2 (the key's lifecycle) · 3 (the unknown state, collisions) · 4

**Short answer for the interview:** "The duplicate is a retry of a non-idempotent write, so I'd make the charge idempotent. When the associate starts the payment the client generates one idempotency key, a random UUID, persists it with the pending sale and sends it on every retry. The server stores key and result under a unique constraint and returns the original result for a repeat, so a retry can never charge twice. On the frontend, Pay is single-flight, and a timeout after sending is an unknown state, not a failure: the screen says 'checking payment', asks the server for the status of that key, and only offers a retry when the server confirms nothing was charged."

**Study:** `JavaScript.md → ### When the framing itself is wrong` (the double-clicked Save row) · `React.md → ## Optimistic UI: three mutations in flight and one fails` · `Design Patterns.md → ## Single-flight` · already listed in `Vacantes/Nordstrom.md → # Still to study` ("Payment-flow reliability") · outside: Stripe docs "Idempotent requests" (key lifecycle, replayed responses, 24h retention); IETF draft "The Idempotency-Key HTTP Header Field".

**Related trap:** "Debounce the Pay button" — a UI-timing hack; the network can duplicate the request regardless.

## 2. [Hyatt · EXTRA] Hydration mismatch on a room card — ❌

**Question:** Hotel search page, Next.js App Router. In production the console shows "Hydration failed because the server rendered HTML didn't match the client", and QA says the "Rooms" label does not focus the input when clicked. Find every bug in `RoomCard`, explain why each one happens, and write the fixed component. ~15 minutes.
*Follow-ups:* (1) Would saving `Math.random()` in a variable fix the hydration error, or only the label? (2) Which other lines differ between server and client? (3) Write the code. Unanswered — moved on with `next`.

```tsx
'use client';
export function RoomCard({ room }: { room: Room }) {
  const currency = typeof window !== 'undefined' ? localStorage.getItem('currency') ?? 'USD' : 'USD';
  const minutesAgo = Math.round((Date.now() - room.priceUpdatedAt) / 60000);
  return (
    <article>
      <h3>{room.name}</h3>
      <p>{formatPrice(room.price, currency)}</p>
      <small>Price updated {minutesAgo} min ago</small>
      <label htmlFor={`qty-${Math.random()}`}>Rooms</label>
      <input id={`qty-${Math.random()}`} type="number" min={1} />
    </article>
  );
}
```

**What I said:** "a desynchronization between 2 values … we use `Math.random()` to generate the `htmlFor` and input id, the values don't match … we can save it in a variable before, or use a value of the room, or a library like crypto". No code.

**What was wrong or missing:** Found the label/input mismatch (QA's bug), and `room.id` points the right way. But a random value saved in a variable still differs between server and client, so the hydration error stays — and "a library like crypto" is still random. Missed the other two mismatches: the `typeof window` branch (server renders USD, browser renders the stored currency) and `Date.now()` (minutes differ between server render and hydration). Root misconception: `'use client'` does not mean client-only rendering; the component is server-rendered and then hydrated. No code.

**Missing beat:** 2 (why hydration compares server and client output) · 3 · 4

**Short answer for the interview:** "A `'use client'` component is still server-rendered, then hydrated, and the first client render must produce the same HTML. Three lines break that: `Math.random()` IDs, which also break the label link — `useId` gives a stable ID on both sides; the `typeof window` branch that reads `localStorage`, where the server says USD and the browser says EUR — I'd move the currency to a cookie so the server renders the right one, or use `useSyncExternalStore` with a server snapshot; and `Date.now()`, which drifts between render and hydration — compute it after mount or render an absolute time."

**Study:** not in the vault — `React.md` only covers hydration conceptually (`## Hydration, explained to a non-technical PM`). Already listed in `Vacantes/Hyatt.md → # Still to study` ("Hydration mismatches"). Outside: react.dev `hydrateRoot` → "Handling different client and server content"; react.dev `useId`; Next.js docs "Text content does not match server-rendered HTML" error page.

**Related trap:** "`useEffect` + `useState` fixes it" — it does, but the user sees USD flash to EUR. Reading the preference on the server (cookie) removes the flash.

```tsx
// Reference solution
'use client';

import { useEffect, useId, useState, useSyncExternalStore } from 'react';

function subscribeToStorage(onChange: () => void) {
  window.addEventListener('storage', onChange);
  return () => window.removeEventListener('storage', onChange);
}

function useStoredCurrency() {
  return useSyncExternalStore(
    subscribeToStorage,
    () => localStorage.getItem('currency') ?? 'USD',
    () => 'USD', // server snapshot — also used during hydration
  );
}

function useMinutesSince(timestamp: number) {
  const [minutes, setMinutes] = useState<number | null>(null);
  useEffect(() => {
    const update = () => setMinutes(Math.round((Date.now() - timestamp) / 60000));
    update();
    const id = setInterval(update, 60_000);
    return () => clearInterval(id);
  }, [timestamp]);
  return minutes;
}

export function RoomCard({ room }: { room: Room }) {
  const qtyId = useId();
  const currency = useStoredCurrency();
  const minutesAgo = useMinutesSince(room.priceUpdatedAt);

  return (
    <article>
      <h3>{room.name}</h3>
      <p>{formatPrice(room.price, currency)}</p>
      <small>
        {minutesAgo === null ? 'Price recently updated' : `Price updated ${minutesAgo} min ago`}
      </small>
      <label htmlFor={qtyId}>Rooms</label>
      <input id={qtyId} type="number" min={1} />
    </article>
  );
}
```

## 4. [Securin · EXTRA] Indirect prompt injection in the dashboard assistant — ⚠️

**Question:** Our dashboard has an AI assistant that summarises vulnerability reports, including text from customer-submitted tickets, and it has tools to create Jira tickets and change a finding's severity. A pentester got it to downgrade a critical CVE to "low" just by writing text inside a ticket. What happened, how would you design the defences, and as the frontend lead, how would you get the team to adopt them?
*Follow-ups:* (1) Does the system-prompt rule hold against "SYSTEM OVERRIDE…" in a ticket, and why? (2) The severity tool stays — what goes between the model's decision and the change? (3) How do you get the team to adopt it? Only (3) answered; (1) and (2) open — moved on with `next`.

**What I said:** "this vulnerability is named prompt injection … the AI is considering the text itself as part of the instructions … 1) add rules in the system prompt telling the AI to ignore the content of the ticket when it seems to modify the status … if that isn't enough, restrict the tool access" · on adoption: "explain to the team the purpose of each tool and the importance of minimal permissions … if an LLM's purpose is to read and summarise, it makes no sense that it has access to the rest of the tools".

**What was wrong or missing:** Right name, right mechanism in one line, and least privilege is the correct core control. But the system-prompt rule was offered as the first defence: it is not a control — instructions and data share one channel, and an attacker can always write a more convincing instruction. Missed the word **indirect** (the payload came through data, not from the user). Missed: the tool call must be authorised with the **user's** permissions (otherwise the model is a confused deputy), **human confirmation** for any write (the UI shows the proposed change; the analyst clicks Confirm), untrusted content marked as data, audit log, and red-team tests in CI. Adoption answer was "explain it" — no mechanism (threat model in the design review, a shared tool-permission wrapper as the default, an eval suite of injection cases that blocks merges).

**Missing beat:** 2 (why prompt rules fail) · 4 · lead layer

**Short answer for the interview:** "That's indirect prompt injection: the instruction arrived inside data the model read, and the model can't reliably tell instructions from data. So I don't rely on the system prompt — that's a mitigation, not a control. The controls sit outside the model: the summariser gets read-only tools, any write runs with the analyst's own permissions, and a severity change is only a proposal the UI shows for the analyst to confirm, with an audit log. To make it stick, I'd put it in one shared tool wrapper so it's the default, and add a set of injection cases to CI so a regression fails the build."

**Study:** `Security.md → # How do you handle security threats in the app?` covers web security only — AI security is not in the vault. Already listed in `Vacantes/Securin.md → # Still to study` ("AI security: direct vs indirect prompt injection…"). Outside: OWASP Top 10 for LLM Applications — LLM01 Prompt Injection and LLM06 Excessive Agency; Simon Willison "The lethal trifecta" (private data + untrusted content + exfiltration); the confused-deputy problem.

**Related trap:** "We'll detect injections with another LLM as a classifier" — it helps, but it is probabilistic; the hard guarantee is still permissions plus human confirmation.
