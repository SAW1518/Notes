# Where to improve

## Technical
- **Duplicate events vs duplicate effects.** Reached for debounce, a timer, on a correctness problem. A double charge can come from a retry after a timeout, where no UI trick helps. The fix is an in-flight guard plus an **idempotency key** the server deduplicates on.
- **A timeout is "unknown", not "failed".** Not yet part of the reflex when a network write is involved.

## Answer habits
- **Answered half the question.** The question asked for frontend *and* backend; the answer stopped at the frontend.
- **Listed options without choosing.** "Debounce, or another option could be disable the button" — pick one and say why the other is worse.
- **One-line answer for a design question.** A store-floor payment needs the four beats: the guarantee, the mechanism, the failure mode, how to measure it.
- **"I'm not sure" was the right call** on the follow-up. Credit kept: honesty beats inventing.

## English
- "this **look** like" → "this **looks** like" (third-person *-s*).
- "another option **could be disable** the button" → "another option **would be to disable** the button" / "another option is **disabling** the button".

# Questions

## 1. [Nordstrom · VAULT] Charging a card exactly once — ❌

**Question:** On POS+, an associate taps "Charge card" on slow Wi-Fi, nothing happens for three seconds, and they tap twice more. How do you make sure the customer is charged exactly once, in the React frontend and on the backend?
*Follow-ups:* (1) With a 500 ms debounce and a 3 s request, what happens on the third tap? (2) The button is disabled, the request times out at 10 s and shows "Payment failed", but the server did charge. The associate taps again — what prevents the second charge, and what must the backend guarantee?

**What I said:** "this look like a clasic debaunse aplcatio … we can add an smoll time to avoid duplicate evnts or anoter opcion cul be deable the but after the first action an add a loader spiner". Follow-ups: "no sure".

**What was wrong or missing:** Debounce is time-based and doesn't know a request is in flight, so the third tap at 3 s goes through. The timeout case is a retry, not a tap. The answer needs: an in-flight guard (a state machine plus a `useRef` flag), one idempotency key per payment attempt reused on every retry, treating a timeout as *unknown* (retry with the same key or check the status), and a backend that stores key → result under a unique constraint and replays the stored response.

**Missing beat:** 2 (mechanism) and 3 (failure mode).

**Short answer for the interview:** "Disabling the button only stops duplicate clicks, not duplicate charges. The frontend creates one idempotency key per payment attempt, sends it on every retry, and treats a timeout as *unknown*, not *failed*, so it retries with the same key or checks the status. The backend stores the key with the result, so a repeated key returns the original response instead of charging again."

**Study:**
- Vault: [[JavaScript#Debounce vs throttle]] (the "Double-clicked Save → Neither" row) · [[React#Optimistic UI: three mutations in flight and one fails]]
- Outside: Stripe docs, "Idempotent requests" · IETF draft "The Idempotency-Key HTTP Header Field" · RFC 9110 §9.2.2, "Idempotent Methods"

**Related trap:** making the payment optimistic. Never show "Paid" before the server confirms.
